# MaintFlow production checklist

Production Supabase is `maintflow-production` (`tkofnsyqywhixuotbiet`, Tokyo, PostgreSQL 17). The private VPS rehearsal verified the staging artifact, loopback binding, static assets, staging connectivity and portal isolation. Production recovery, release approval and first activation each have a separate verification step below.

## Staging credential retirement

1. Open the [staging API Keys page](https://supabase.com/dashboard/project/dmrmqrtjmpeyoekicctp/settings/api-keys) and verify the project reference is `dmrmqrtjmpeyoekicctp`. Identify the previously shared credential from its original entry. A legacy `service_role` key is a JWT beginning with `eyJ`; a modern secret key begins with `sb_secret_` and has its own entry under **Publishable and secret API keys**. Identify the entry without copying the old or new value into chat, Git, or a ticket.
2. Under **Publishable and secret API keys**, create a named replacement secret key and save it in the approved secret manager. Keep the application's existing variable name `SUPABASE_SERVICE_ROLE_KEY`. Replace it in any active staging app runtime, staging-targeted local environment, or automation that uses the old key. The stopped VPS rehearsal keeps its environment at `/etc/maintflow/rehearsal.env`; update it through the provider's approved secret channel only if a new rehearsal is needed. Check for staging scripts, integrations and secret copies outside the repo before retiring the old key. The staging build uses only the public URL and publishable key.
3. Run a read-only staging API check with the replacement key from a trusted runtime and record only the result. For a modern key, delete its old entry from **API Keys** after verification. This leaves legacy API keys, JWT signing and user sessions unchanged.
4. For a legacy service-role JWT, confirm all staging clients use modern publishable or secret keys, including any old local test clients. In **Settings → JWT Keys → JWT Signing Keys**, migrate the legacy JWT secret if needed and rotate to an asymmetric standby key. Allow the configured access-token lifetime plus a buffer for sessions to refresh. Supabase gives one hour and 15 minutes as the example for a one-hour expiry. In **API Keys → Legacy anon, service_role API keys**, disable the legacy pair. Then return to **JWT Signing Keys → Previously used keys** and revoke the legacy signing secret. Existing access tokens signed with the old secret can fail after revocation if they have yet to refresh. Verify the replacement works and the retired key fails, recording status only. Get approval for the staging maintenance window before making changes.

[Supabase credential retirement procedure](https://supabase.com/docs/guides/security/rotate-leaked-api-keys) · [JWT signing key migration](https://supabase.com/docs/guides/auth/signing-keys)

## Production database and backups

- Keep the development and staging projects in their existing roles. The release checks reject both project references. Production is on Free and can be paused for inactivity. Use a modern publishable key for the client, a dedicated modern secret key for the server, and an independent random `AUTH_RATE_LIMIT_SECRET`. Use the production project for all values in the [pull runbook](README.md#production-after-separate-cutover-approval). Use the canonical HTTPS origin, restrict redirect URLs to the approved application paths, and have the owner approve disabling public signup before employee onboarding.
- The November 22, 2026 read-only production check confirmed `disable_signup=true`, email as the only enabled provider, and anonymous sign-ins disabled. There were zero Auth users, identities, sessions, and application profiles. Reconfirm these Auth settings before first onboarding and cutover.
- Production catalog definitions match staging across columns, constraints, indexes, functions, grants, triggers, policies, RLS and enums. The three production migration records contained the same SQL as the committed files. Their versions now match the filenames (`20261121153336`, `20261121153426`, `20261121153505`). The reconciliation updated version IDs only. Keep the historic `database/` scripts as reference and use `supabase/migrations/` for new deployment work.
- Keep RLS enabled with no end-user policies on `auth_rate_limits` and `work_order_reopening_history`. Neither anonymous nor signed-in roles have direct read/write access. The signed-in inventory and spare-part RPCs authorize the caller and enforce the write guards. The role and password-readiness helpers are used by RLS and return only information about the caller. Keep anonymous execution disabled for all four functions.
- Assign a backup and recovery owner. Configure nightly encrypted offsite exports, alerts, retention and a disposable restore drill using the [backup procedure](supabase-free-backups.md). Require the first successful export and restore before accepting real records. Free includes neither automatic daily backups nor point-in-time recovery. [Supabase backup plans](https://supabase.com/docs/guides/platform/backups)

### First production administrator

1. Obtain explicit owner approval for the initial person and employee number. Use a named account and verify the email address out of band. Keep login material in the person's password manager. Provisioning requires a production Supabase administrator with access to Auth and SQL. The VPS provider has no role in this step.
2. In the production project only, with public signup disabled, use the Dashboard's administrative user creation. The approved administrator enters a password privately using their password manager during the supervised setup. Confirm the email only after verifying ownership. Capture the Auth UUID locally. If automating the administrative step later, Supabase's server-side `auth.admin.createUser` accepts a modern secret key. The application's employee-creation route cannot bootstrap the first admin because it requires a signed-in admin profile. [Supabase admin createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser)
3. In a transaction, check that the approved Auth UUID and verified email resolve to exactly one row, that no administrator profile exists, and that neither the UUID nor employee number already has a profile. Insert the matching row in `public.users` with role `admin`, the same Auth UUID and email, and the approved name and employee number. The employee number must contain 1–20 digits without a leading zero. Use `must_change_password=false` only when the administrator set their own password privately. Stop on any mismatch. Record the approved account verification without publishing personal data.
4. Confirm the two records are linked and exactly one administrator exists before provisioning other users. Document account recovery responsibility. If profile creation fails, keep the created Auth account holder and operator informed and correct the profile after checking the same UUID, without recreating the account.

## Release approval and first cutover

Use the [provider handoff](provider-cutover.md) for the single server session after the owner has cleared the production prerequisites.

1. GitHub environments `maintflow-build-production` and `maintflow-publish-production` are configured with the public production settings and allow only the exact `maintflow-release-control` branch. The publish environment requires the sole reviewer `AbdalmalekSlman` and administrator bypass is disabled. Self-review is enabled so the owner can submit and record approval. Before installing the workflow on a separately authorized control branch, restrict changes to trusted maintainers. Keep the build token read-only and allow repository write, OIDC and attestations only in the publish job. Before approving the first publish job, verify it is waiting for review and confirm that `deploy` has not moved. Record the source SHA, release checksum and attestation after an authorized publication. See the [pull runbook](README.md#production-after-separate-cutover-approval).
2. Consolidate provider work into one scheduled cutover. Have the provider preserve the Flask service, configuration and data, install and verify the pinned MaintFlow units and protected runtime environment, and run the pull installer in preparation mode. Run the candidate on loopback and verify the readiness marker, public assets and a read-only production database check. Leave Flask serving until the candidate passes and the owner approves the switch.
3. Stop the candidate, pause the legacy updater, release port 8100 from Flask, set the initial validated release as current, and start MaintFlow. Verify the HTTPS homepage, a static asset, protected routing, journal and memory headroom. Validate any approved nginx configuration with `nginx -t` before reload.
4. If initial activation fails, stop MaintFlow, restore any changed nginx configuration, restart Flask and verify HTTPS before resuming its updater. After a stable first cutover, enable the MaintFlow updater. It will validate new releases, retain the current and previous two successful releases, and restore the prior release if a later activation fails.
